# Concrete numeric values for particle bursts, hit flashes, UI/level-up feedback and post-processing flashes in 2D action games

**Researched:** for the Inkfall project (2D top-down action).
**Method:** ~15 web searches, ~30 pages actually fetched. Every number below is tagged with the URL it came from.
**Honesty rules used in this document:**

- `[cited]` — the number comes from a page I fetched. The URL is in the table.
- `[experiential inference]` — my own synthesis/opinion, clearly labelled. Not a source.
- `[secondary, unverified]` — the page exists and I fetched it, but it is AI-authored or SEO/training content whose internal claims I could not corroborate. Treat the whole row as a hypothesis, not evidence.
- **Anything I only saw in a search-result snippet and could not fetch is listed in the appendix as unusable.** It is not used in the tables.
- Sources conflict in several places. Conflicts get their own callout boxes — read them before picking numbers.

**Engine versions referenced:** Godot 4.x (`stable` docs + `master` branch engine XML), Unity 6.1 / 6.6 URP docs, Unity VFX Graph 10.8 docs.

### §1 notes and a real conflict

> **CONFLICT — how many particles is "normal" for a big effect?**
> UWA (production Unity optimisation, 2019) says **one skill effect ≤ 50 particles** and **400+ is excessive**.
> A training-school article (2026) says **mobile 200–300 per effect, PC 2000–5000**.
> These are not reconcilable as stated. The likely resolution: UWA's 50 figure is for a *single hit/skill* on mobile-era hardware with old GPU budgets, while the 200–5000 figures are for *ultimate-ability / boss-cinematic* effects, and for stylised versus realistic rendering. `[experiential inference]`
> **Recommendation:** treat 50 as your *per-hit* ceiling and 200 as your *per-ultimate* ceiling, and verify with your own fill-rate measurement.

> **CONFLICT — is particle count even the metric?**
> UWA is explicit: on the CPU side "the number of particles matters very little compared to the number of particle *systems*"; the expensive functions are `ParticleSystem.Update` and `ParticleSystem.ScheduleGeometryJobs`. On the GPU side "overdraw is the particle system's biggest killer". `[cited]`
> **Therefore:** measure **emitter count** and **overdraw fill multiplier**, not particle count. A 12-particle burst of 64×64 additive sprites is worse than a 60-particle burst of 8×8 sprites.

### §2 notes and a real conflict

> **CONFLICT — 50–100 ms vs 100–200 ms.**
> - 100–200 ms, with the explicit warning that >200 ms looks like "catching fire" (Godot tutorial author).
> - 50–100 ms, with 30 ms "too fast" and 150 ms "blurry" (secondary/AI blog).
> - 1–3 frames ≈ 17–50 ms (secondary AI skill doc).
> - 120 ms and 150 ms from the two Godot code samples.
>
> **Reading `[experiential inference]`:** everybody agrees the band is roughly 50–200 ms and that below ~50 ms you lose it and above ~200 ms it becomes a state change rather than an impact. Start at **120 ms** (the median of the actual published code defaults) and tune by hit weight. Note the two *code samples* — the most trustworthy kind of evidence here — both use 120 ms and 150 ms, i.e. the top of the "flash" band, not the bottom.

> **What engine devs actually implement (answering the question directly):** a `canvas_item` / sprite shader with a `float flash_amount` uniform and `mix(original_rgb, flash_rgb, flash_amount)`, driven by a Tween from 1.0 → 0.0 over the duration, with the material duplicated per instance. `modulate`/multiply is the approach people reach for first and it is documented to not work on dark sprites. `[cited]`
> No fetched source recommends **screen** blend for the enemy hit flash itself; "additive" is discussed only as a hazard (Sakurai). Screen blend appears in Godot's *glow* system (`GLOW_BLEND_MODE_SCREEN` is the default glow blend mode), not in hit flashes. `[cited]`

### §3 notes

**Non-uniform vs uniform:** every concrete code sample I found that reacts to an *impact* uses **non-uniform** squash (e.g. `(1.3, 0.7)`), while the "hit pop" samples use **uniform** scale-up (`×1.25`). `[cited]`
`[experiential inference]` In a top-down 2D game the visual "axis" of an impact is ambiguous, so uniform pop is safer for hits and non-uniform squash is best reserved for landing/ground-slam and for directional knockback (squash along the knockback vector).

**Volume preservation:** one source states the rule formally — "if width scales by 1.5×, height scales by ~0.67× (`1/1.5`)" — and provides `1.0 / primary_scale` for 2D. `[secondary, unverified]` It is standard animation practice; I'd apply it, but note the source is unverified.

### §4 notes — a genuine, important conflict

> **CONFLICT — hit-stop: 50–100 ms (folk wisdom) vs 390 ms (peer-reviewed).**
> - Four secondary sources converge on **50–100 ms**, and one explicitly warns that longer "makes players think the game is lagging".
> - The VISIGRAPPA 2024 paper measured a **0.39 s** hit-stop as the average *comfortable* one, and found stressfulness rises monotonically with duration.
>
> These are not the same effect. The paper's hit-stop **prolongs the enemy's death animation at 1 % playback speed** — it is a dramatic slow-motion death, not a whole-game impact freeze. The folk-wisdom 50–100 ms is a whole-world or attacker+target freeze on an ordinary hit. `[experiential inference]`
> **Practical synthesis:** 50–100 ms for ordinary hits; escalate to 150–250 ms for a critical or a kill; reserve anything near 400 ms for a rare boss-death / finisher cinematic. Never put 400 ms hit-stop on a repeatable attack — that is exactly the "game is lagging" failure the secondary sources warn about, and the paper's own data shows discomfort climbing with duration.

> **Level-up specifically:** I found **no** published breakdown of a game's level-up celebration timing. The concrete guidance that exists is generic UI motion timing (M3 tokens, 100 ms feedback rule, 80–120 ms button press). Any level-up number is therefore composition, not citation. `[experiential inference]` A defensible recipe: banner scale-in with overshoot over **250 ms** (`standardIncoming`), glow pulse ×1.4 over **200 ms** then decay **400 ms**, hold the celebration **1.2–2.0 s**, dismiss over **150 ms** (`emphasizedOutgoing`).

At 60 fps that is 17–50 ms — a snap, not a spark | https://raw.githubusercontent.com/gamedev-skills/awesome-gamedev-agent-skills/refs/heads/main/skills/disciplines/game-feel/references/feedback-recipes.md |
| Hit-mark design rules (Sakurai, 7 required conditions) | ① Flashiness matching the effect; ② **has contrast** (thin/hazy = no); ③ appropriate hit position; ④ **combine various elements** (not one piece of art — add shockwaves, sparks) though too cluttered is a problem; ⑤ **don't hide the character too much**; ⑥ **appropriate on-screen duration — short for consecutive hits, longer otherwise**; ⑦ **vary brightness — place dark colours too** so it is visible on bright or dark backgrounds. "Since most hit marks keep moving during hit-stop, you should make good use of the lengthened staging time." Juice It Or Lose It: on every hit the ball becomes white **and** is resized bigger and wobbles and rotates, with smoke puffs **and** unique particles `[cited]` | Layer order: **(1) white flash on the enemy sprite, (2) dark-cored shockwave ring behind it, (3) spark particles on top, (4) scale pop.** The dark core is what makes the white flash readable on a bright floor | https://en.senkohome.com/sakurai-game-dev-effect/ ; https://devblog.heisarzola.com/gdcr-juice-it-or-lose-it/ |

## 8. Master table — VFX budgets and readability in 2D

| Effect | Value | Recommended range for a 2D top-down action game | Source URL |
|---|---|---|---|
| Per-effect particle and draw-call budget (production) | One skill effect: **≤ 50 particles, ≤ 10 draw calls** (older strict standard). 400+ particles in one effect = "too many no matter how you look at it". **5–60 particle emitters inside one effect is "already the wrong approach"** `[cited]` | ≤ 10 draw calls per effect. **Keep emitters per effect ≤ 3–4** — that is the rule most 2D games break, and UWA calls it the wrong approach outright | https://blog.uwa4d.com/archives/TechSharing_169.html |
| Active particle systems on screen | **< 50 active particle systems on low/mid-end devices** `[cited]` | **Cap concurrent emitters at ~30–50.** With 20 enemies dying at once this is the limit you will hit first | https://blog.uwa4d.com/archives/TechSharing_169.html |
| What actually costs CPU | "The number of particles matters very little on the CPU side compared with the number of particle **systems**." Watch `ParticleSystem.Update` and `ParticleSystem.ScheduleGeometryJobs` `[cited]` | Budget **emitters**, not particles. Pool a small number of emitters and re-point them (`restart()`) rather than instancing new ones per death | https://blog.uwa4d.com/archives/TechSharing_169.html |
| What actually costs GPU | "**Overdraw is the particle system's biggest killer.**" Warning threshold: average fill multiplier **> 3** (**> 4** without a skybox) or single frame **> 5**. Measured bad case: **12×** average fill. Fine case: 90 overlapping particle layers with total fill rate **2** `[cited]` | Measure **fill multiplier**. Rule of thumb: keep total screen-fill of transparent VFX under ~3× and never let a single frame exceed 5×. Enforce a **maximum particle sprite size** — one screen-sized additive sprite is the classic killer | https://blog.uwa4d.com/archives/TechSharing_169.html |
| Readability: don't bury the character (Sakurai) | "For the sake of impact, the character can get buried in the effect and become hard to see. Fairly common. **In a 2D game it's easy: raise the character's display priority above the effect.** No issue with the look either." Also hit-mark rule ⑤ "don't hide the character too much", and rule ⑦ "vary brightness — place dark colours too" `[cited]` | **In a 2D top-down game, put the enemy/player sprite on a higher z-layer than the death and hit VFX.** This is the single strongest readability lever available to us and it is explicitly recommended for 2D by a first-party source | https://en.senkohome.com/sakurai-game-dev-effect/ |
| Readability: contrast on bright backgrounds | "Effects tend to get bright, so **deliberately mixing in dark ones** makes them visible even on bright screens and adds contrast… it's good to think about setting things off with their opposite, like adding straight lines to curves." Hit marks must have contrast — "thin fibres or being unclear via additive colour are lacking" `[cited]` | Every bright VFX must ship with a dark element (a dark core, an outline, or a shadow). Non-negotiable for a game on a light floor | https://en.senkohome.com/sakurai-game-dev-effect/ |
| Readability: screen shake hazard | "It can make the screen hard to see, so **beware overdoing it**." Two methods: move the camera (distant view may not move; devise the focus point) or move the rendered image (whole screen including UI shakes, but **black blanks may appear at the screen edges**). Smash's shake comes in large/medium/small and continuous patterns that "**change the vibration pattern itself** — vertical only, plus horizontal, an earthquake-like continuous shake". Strength is "**strong at first, then gradually settling**, with a pleasant degree of randomness" `[cited]` | Keep shake ≤ 6–10 px so no black edges appear. Use **different patterns** (vertical-only vs vertical+horizontal) for light vs heavy rather than only scaling amplitude | https://en.senkohome.com/sakurai-game-dev-effect/ |
| Readability: scale of the effect | "Beware flames looking candle-sized… a common snag. A flame the same size or bigger than the character looks like a candle or torch. The problem is **insufficient granularity** in how it is drawn… increase the loop count of drawing flame as flame. Effects keep moving, so they don't need to be very fine. **Rough and fast is the point.**" `[cited]` | A death effect bigger than the enemy must have granularity (many small elements), not just a scaled-up version of the small effect. This is why the boss burst needs more than a scaled common-enemy burst | https://en.senkohome.com/sakurai-game-dev-effect/ |
| Readability: Sakurai on observing | "Effects flood you with all sorts of information in an instant, so they're **hard to catch with the eye**… Whatever you make, **observing well is the shortcut**. Slowing it down shows the motion well… try cutting them and it's bland beyond compare." He demonstrated by viewing Smash Ultimate's effects in slow motion with no background `[cited]` | **Build a debug key that plays your hit effect at 0.1× speed on a plain background.** This is the cheapest quality-control tool in this entire document | https://en.senkohome.com/sakurai-game-dev-effect/ |
| Overdraw budget on mobile `[secondary, unverified]` | Semi-transparent area within **15 % of the screen** on mobile (30 % on PC). Texture resolution conventions: UI FX 256², skill FX 512², ultimate FX 1024² | 15 % of screen for transparent VFX is a stricter and probably more useful budget than UWA's fill multiplier for a 2D game. Texture sizes are worth adopting as a convention | https://www.2ds.cn/商业游戏特效规范：手游与端游的特效制作标准差异-16/ |
| Readability litmus test `[secondary, unverified]` | The "three-second rule": show the effect to a non-artist colleague for 3 seconds; if they cannot quickly identify the skill type (fire/ice/lightning), the visual information is overloaded. "The core of commercial game VFX is **readability**, not gorgeousness." | Good test for a top-down game: can the player identify what killed them within 3 seconds of a busy screen? | https://www.2ds.cn/商业游戏特效规范：手游与端游的特效制作标准差异-16/ |

## 9. Conflicts and how I resolved them

| # | Conflict | Sources | Resolution |
|---|---|---|---|
| 1 | **Big-effect particle counts** — 50 vs 200–300 vs 2000–5000 | UWA production standard `[cited]` vs training-school article `[secondary]` vs same `[secondary]` | Treat 50 as the per-hit ceiling, 200 as the per-ultimate ceiling. Never ship 2000+ in 2D. `[experiential inference]` |
| 2 | **Hit-stop duration** — 50–100 ms vs 390 ms | Four secondary sources vs one peer-reviewed study `[cited]` | They measure different effects (world freeze vs slow-mo death). 50–100 ms for repeatable hits; escalate only for rare finishers. |
| 3 | **Hit-flash duration** — 1–3 frames (17–50 ms) / 50–100 ms / 100–200 ms / 120 ms / 150 ms | AI skill doc, AI blog, Godot tutorial ×2 `[cited]` | The two published *code defaults* are 120 ms and 150 ms. Start at 120 ms. |
| 4 | **Bloom default intensity** — 0 (Unity URP) vs 0.3 (Godot glow) | Unity vs Godot docs, both `[cited]` | Different scales entirely; Unity 0 = "disabled", Godot 0.3 = "on but subtle". Do not copy numbers between engines. |
| 5 | **Bloom in 2D** — threshold 1.0 default vs "must be below 1.0 in 2D" | Godot's own docs `[cited]` | Godot's own docs contradict their own default for the 2D case. Set 0.9. |
| 6 | **Chromatic aberration** — no engine documentation at all vs a detailed secondary recipe | Unity URP docs (intensity only) vs one AI-generated repo `[secondary]` | Present every CA px/ms number as unverified. |
| 7 | **Whether the flash should be additive** | Sakurai (additive goes hazy, loses contrast, only works on dark screens) `[cited]` vs Juice-It-Or-Lose-It-style "make it white" `[cited]` vs the Godot hit-flash tutorials (mix, not additive) `[cited]` | **mix() to a colour, not additive.** Additive is for the *burst particles* on top, with a dark core underneath. |
| 8 | **Camera shake magnitude** — 20 px (Bevy official) vs 2–10 px (two secondary sources) | Bevy example `[cited]` vs `[secondary]` | Bevy's example is a demo, not a game recommendation, and it has no UI to keep on-screen. Use 6–10 px. |
| 9 | **Is `randomize`/`randomness` needed?** — Godot defaults are all 0.0 | Godot docs `[cited]` | Defaults are 0 everywhere, which makes a burst look mechanical. Raise lifetime randomness to 0.3–0.5. `[experiential inference]` |

## 11. Source quality key (read this before quoting me)

**Developer / first-party — highest trust**
- Godot engine source `doc/classes/*.xml` (the actual class reference data) and `godot-docs` raw RST — `[cited]`
- Unity Manual (URP post-processing, Particle System Main module) and VFX Graph package docs — `[cited]`
- Bevy official example `2d_screen_shake.rs` — `[cited]`
- W3C WCAG 2.3.1 Understanding — `[cited]`, and a standards document rather than a blog
- UWA (Unity performance-optimisation company) production Q&A — `[cited]`, real production experience, though from 2019
- 80.lv / Bryan Singh, 2017 — `[cited]`, a named game designer describing shipped technique (no numbers though)
- Tomizawa & Ishikawa, VISIGRAPPA 2024 (peer-reviewed, CC BY-NC-ND) — `[cited]`, the best hit-stop source available

**Developer blog / tutorial — medium trust**
- `cursogame.dev` Godot hit-flash tutorial — `[cited]`; publishes working shader + `flash_duration = 0.15` default plus explicit tuning advice. Most useful single page in this research.
- `dev.to` / saltmire Godot game-feel tricks — `[cited]`; publishes copy-pasteable defaults (0.12 s flash, 0.25/0.25 s pop). The author joined DEV in 2026 and sells a paid tool, so treat the *defaults* as code evidence and any *claims* about their superiority with mild suspicion.

**Secondary, unverified — treat as hypotheses**
- `raw.githubusercontent.com/raduacg/game-mechanics-optimizations/*` — the file naming, the "Algorithmic Complexity / Measurement / Profiling / Examples from Shipped Games" structure, and the confident per-game numbers (Celeste 20 %, Dead Cells 0.6×, Cuphead 0.4–2.0×) are strong AI-generation fingerprints. The **parameter ranges are usable**, the **shipped-game attributions are not**.
- `raw.githubusercontent.com/gamedev-skills/awesome-gamedev-agent-skills/...` — an AI-produced agent skill document. Its tier table (0–4 / 6–12 / 20–40 particles; hit-stop none / 0.04–0.06 / 0.10–0.15 s) is coherent and internally consistent, which is why I include it, but it cites nothing.

Its numbers agree with other sources more often than not.
