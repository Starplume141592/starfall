## 一、怎么读出来的（可复现）

工具留在 `.dsh/`（未纳入 git）：

| 脚本 | 作用 |
|---|---|
| `.dsh/pck.mjs` | 解析 `.pck`：目录起点与元数据块长度**自动推断**，支持 `list` / `cat <正则>` / `extract <目录> <正则>` / `check` |
| `.dsh/gdc-strings.mjs` | 解出 `.gdc`（GDScript 字节码）里的字符串表 |
| `.dsh/gdc-grep.mjs` | 在整棵 `.gdc` 树上按关键词搜索 |

**这个包有三处不标准，普通 Godot 解包工具会栽在这里**：

1. **目录起点是 84 字节**（Godot 3 布局：magic + 版本三件套 + 64 字节保留 + file_count），**没有 Godot 4 的 `file_base` 字段**。
2. **每条目录记录的元数据块是 32 字节**（`offset u64` + `size u64` + `md5 16B`）—— **没有标准格式里的 `flags u32`**（那会凑成 36 字节）。按 36 字节读会在第二条记录上崩。
3. **路径字段按 4 字节对齐填充，且填充长度算在 `sl` 里**。路径必须**在第一个 NUL 处截断**；否则带填充的条目会被 `$` 锚点漏掉（我第一次就漏了 2929 个文件）。

**另外，`.gdc` 里的字符串表被 XOR `0xB6` 编码过**（数字与头部未编码）。`f4 d7 c5 d3 e5 de d9 c6` ^ `0xB6` = `BaseShop`。所以直接 `strings` 搜不到任何标识符——必须先 XOR。仓库里 30 个 `.gd` 是**明文源码**（`item_data.gd` / `weapon_data.gd` / `weapon_stats.gd` 等），可直接读。

统计：包内 **7416 个文件**，其中 `.tres` 2985、`.tscn` 110+、`.gdc` 约 700、`.gd` 明文源码 30。

## 二、一局的结构（一手）

| 项 | 实测值 | 证据 |
|---|---|---|
| 波数 | **20 波**（另有 `wave_21`，配 `zones/common/endless` → 无尽模式入口） | `zones/zone_1/zone_1_data.tres` 引用 `wave_1..wave_20` |
| 波时长曲线 | **20 / 25 / 30 / 35 / 40 / 45 / 50 / 55 / 60 ×11 波 / 90（W20 Boss）** | 每波 `wave_N.tres` 的 `wave_duration` |
| 纯战斗总时长 | **1050 秒 = 17.5 分钟** | 上表求和 |
| 每波敌组数 | W1:1 → W3:5 → W7:8 → W15/W17:10 → W18:12 → W19:11 → W20:9 | `groups_data` 元素个数 |
| 单波敌人上限 | `max_enemies = 100` | `wave_data` 字段 |
| 波间 | 每波结束**自动进商店** → 一局 **20 次商店** | `zone_data` 结构 + 社区文档一致 |

**交叉验证成立**：我按文件求和得到 **1050 秒**，与 `土豆兄弟拆解.md` 从 wiki/公告独立推出的 1050 秒**完全一致**。两份来源互不依赖 → 这条可以当硬事实用。

**波组的语法**（`zones/wave_group_data.gd` 字段，一手）：

```
spawn_chance / spawn_timing / repeating / repeating_interval /
reduce_repeating_interval / min_repeating_interval / area /
spawn_dist_away_from_edges / spawn_edge_of_map /
is_neutral / is_boss / is_horde / is_loot / prevent_if_elite / prevent_if_horde /
min_difficulty / max_difficulty / min_wave / max_wave
```

注意最后两组：**敌组自带「波次区间」与「难度区间」条件**。也就是说难度和波次不是靠"策划手动排表"，而是**同一套敌组资源在不同波数/难度下自动筛选**。

## 四、武器与构筑的机制（一手）

来自明文源码 `weapons/weapon_stats/weapon_stats.gd`：

```
cooldown (ticks, 60/秒) / damage / accuracy / crit_chance / crit_damage /
min_range / max_range / knockback / knockback_piercing /
scaling_stats = [["stat_melee_damage", 1.0]]   ← 关键
lifesteal / recoil / additional_cooldown_every_x_shots ...
```

**`scaling_stats` 就是 `DECISIONS.md` 待确认表最后一行写的「武器属性缩放（Brotato 式）」** —— 每把武器**自己声明吃哪些玩家属性、系数多少**。这是"属性选择"与"这把武器"之间的咬合点：不同武器吃不同属性，所以玩家的属性投资会**改变哪把武器更值得留**。

`weapon_data.gd` 另有 `upgrades_into` / `previous_upgrade` → **武器升级是"换成另一个 WeaponData 资源"，不是乘一个倍率**。这与 `土豆兄弟拆解.md` 独立得出的"品级无统一倍率、逐武器手调"一致，且指出了**实现方式**：一档一个资源文件（203 件 ≈ 51 种武器 × 4 档）。

**套装（synergy）是 6 格武器槽的真正意义所在**：15 套武器，凑 2/3/4/5/6 件同名套装各给一档加成。**槽位不是"能带几把"，而是"我押哪一套、押多深"。**

## 五、商店与经济的证据（一手：标识符，非数值）

从 `ui/menus/shop/base_shop.gdc` 解出的**真实字段与函数名**（XOR 解码后，一字未改）：

```
_shop_items / _focused_shop_item / _player_pressed_go_button
_reroll_price / _reroll_count / _paid_reroll_count / _reroll_discount
_initial_free_rerolls / _free_rerolls / _has_bonus_free_reroll
_item_steals / get_reroll_price / reroll_price_amount
fill_shop_items / keep_lock / locked_shop_items / get_player_locked_shop_items
_combine_weapon / possible_upgrades / upgrades_into / tier / max_weapon_tier_hash
next_elite_wave / next_elite_type / EliteType / elite_spawn / is_endless_run
```

跨脚本搜到的相关标识符还有：`items_price_hash`、`weapons_price_hash`、`specific_item_price`、`specific_recycling_price_factor`、`increase_tier_on_reroll_hash`、`gain_stats_on_reroll_hash`、`starting_gold`、`gain_pct_gold_start_wave_hash`、`total_bonus_gold`。

**能确证的**：

1. 刷新价格是**算出来的**（`get_reroll_price`，输入含 `reroll_price_amount` / `_reroll_count` / `_reroll_discount`），**不是固定表**。
2. **有免费刷新**（`_initial_free_rerolls` / `_free_rerolls`）——与"刷新是一种资源"的设计一致。
3. **锁定跨波保留**（`keep_lock` / `locked_shop_items` / `get_player_locked_shop_items`）。
4. 价格可被**道具修改**（`items_price_hash` / `weapons_price_hash`），且有**回收价系数**（`specific_recycling_price_factor`）。
5. **刷新本身可以是构筑的一部分**：存在 `increase_tier_on_reroll_hash`（刷新提升品级）与 `gain_stats_on_reroll_hash`（刷新给属性）两类加成 —— **刷新不只是"换一批货"，它能被 build 加成**。
6. 商店与 **elite 波**耦合（`next_elite_wave` / `next_elite_type` 在商店脚本里）→ **精英波信息在商店里预告**。

**没能确证的**：**刷新价的确切公式系数**（在字节码指令流里，未反汇编）；**每次商店是 4 件商品**这一条来自 wiki，**游戏文件里没有直接验证**。

## 七、对《星陨》0.6.0 的直接冲击（我的判断，非事实）

1. **它不是"没有事件"，是"把决策全压在商店"**：20 次商店 × 可付费刷新 + 价格被 build 影响 + 锁定跨波 —— 一局里有 **20 个连续的经济决策点**，而我们计划的是 12 次、且货架静态、且"每买一次全场涨价 60%"（`SHOP_INFLATE`）会让决策在第二次购买时就失效。
2. **槽位靠"套装"才有意义**：15 套 × 2/3/4/5/6 阈值。我们的 `设计稿 §A1` 说"6 格够用、合成会吐回格位"，但**没有任何东西让"带哪 6 把"变成押注**。
3. **武器吃不同属性（`scaling_stats`）才是"火力不是唯一答案"的机制**：它让同样的属性点在不同武器上产出不同，玩家因此要**为自己的 build 选属性**，而不是统一 `dmgMul`。
4. **升级池是 20 属性 × 4 档**，不是"三选一里塞武器强化"。我们的 `A4`（升级不再给武器强化）方向是对的，但**池子必须足够宽**才能承担不确定性——20 项是个量级参考。
5. **变数来自角色（50 个）与难度（6 档），不是来自局内事件**。50 个角色 = 50 种开局约束，这是"这一局和别人不一样"的**主要**来源。
6. **波次/难度不是手排表**：敌组自带 `min_wave/max_wave/min_difficulty/max_difficulty`，同一套资源自动筛选 → 内容量靠"条件组合"而不是"手工排波"。

> ⚠️ 第 1、3、5 条的结论**直接质疑 `DECISIONS.md D-007` 里"事件驱动"作为主骨架**的排法。相关对照与重排建议另出一份（等 `土豆兄弟拆解-压力与失败.md` 到位后合并成结论）。

## 八、实测取证：本机存档与游戏日志（一手）

**取证路径**（本机 Windows）：

```
%APPDATA%\Brotato\<SteamID>\save_v2.json          主存档（局内状态在此）
%APPDATA%\Brotato\<SteamID>\save_v2_NN.json.bak   自动备份（逐波滚动，共 20 个）
%APPDATA%\Brotato\<SteamID>\log.txt               游戏自己的 Run Data 打印
```

存档是**明文 JSON**。本机残留着一次打到 **第 14 波**的完整局内状态（`has_run_state: true`），这就是下面这批数字的来源 —— **全部来自游戏自己写出的状态，不是推算**。

### 8.1 直接读数

| 项 | 实测值 | 出处 |
|---|---|---|
| 波数 | `nb_of_waves = 20` | 存档 |
| **每次商店商品数** | **4 件**（`shop_items[0].Count = 4`） | 存档（第 14 波） |
| **武器槽** | **6**（玩家手上 6 把武器） | 存档 |
| **同名武器可重复** | `weapon_hand` 出现 **2 把**（均 tier 2, value 45） | 存档 |
| **同时锁定格数** | 玩家锁了 **3 件**（`locked_shop_items[0].Count = 3`） | 存档 |
| 开局 | 角色 `character_brawler`，**带 2 把 `weapon_fist_1`**（开局即重复） | 日志 Run Data |
| 材料（gold） | 第 14 波进店前 **321** → 买完东西后 **117** | 存档（相邻两份备份） |
| 第 14 波货架 | `item_knot`(T2,80) · `item_adrenaline`(T2,60) · `weapon_anchor_3`(T2,95) · `item_blood_leech`(T1,45) | 存档 |
| 刷新计数 | `reroll_count = 3`、`paid_reroll_count = 3`、`initial_free_rerolls = 0` | 存档 |
| 道具可重复 | 后期持有 `item_turret_healing ×2`、`item_wings ×2`、`item_clockwork_wasp ×2` | 日志 Run Data |
| 存档版本 / 语言 | `version = 2`、`settings.language = "zh"` | 存档 |
| DLC | `enabled_dlcs = ["abyssal_terrors"]` | 存档 |

**"商店只有 3 件"的假象**：同波的相邻备份里 `shop_items` 会出现 3 件 —— 那是**买走一件之后**的状态（数组被消费）。**完整货架恒为 4 件。**

### 8.2 存档里**没有**的东西

`current_run_state` 的键里**没有任何逐商品价格字段**（`items_price` / `reroll_price` / `weapons_price` / `specific_items_price` 都是**玩家属性修正项**，本例全为 0）。也就是说：

- **商品标价与刷新价都是运行时算出来的，不落盘**；
- 存档能给出"这一波货架是什么、值多少 `value`"，但**给不出价格**。

### 8.3 因此仍然缺的唯一一手数字

**刷新价的确切公式系数。** 已知的只有：它是算出来的（`get_reroll_price`）、有免费刷新、有折扣、能被道具改（`reroll_price` 是玩家属性）、**涨幅远快于商品价**。三条候选公式（W20 ≈ 23 / 16 / 30）在 `土豆兄弟拆解.md §2.4` 并列，仍无定论。

**把它测出来的可行路径**（无需 OCR，纯存档差分）：进一局 → 第 1 波结束时存档会写下 `gold`（进店前）→ 点一次刷新 → 退出到菜单（写盘）→ 再读 `gold`，**差值就是刷新价**；多波重复即可拟合曲线。这条需要真实操作游戏流程，本次未执行完。
